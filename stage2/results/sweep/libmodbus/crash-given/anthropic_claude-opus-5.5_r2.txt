**Root cause:** the write-and-read-registers handler (function code 0x17) in `modbus_reply` checks the read address for negative values twice and never checks the write address. A write address below `start_registers` therefore produces a negative index, and line 980 writes before the start of the `tab_registers` heap buffer.

**How the report leads there**
- The crash is a WRITE SEGV at `modbus.c:980`: `mb_mapping->tab_registers[i] = ...`.
- At that point `i` starts at `mapping_address_write`, which is computed at line 953 as `address_write - mb_mapping->start_registers`.
- `address_write` is a `uint16_t` taken straight from the request. If it is smaller than `start_registers`, `mapping_address_write` is negative.
- The faulting address, `0x505ffffffec8`, is just below what looks like a heap region. That fits a write at a negative offset before the buffer.

**The faulty check (lines 962–965)**
```c
} else if (mapping_address < 0 ||
           (mapping_address + nb) > mb_mapping->nb_registers ||
           mapping_address < 0 ||                       /* <-- should be mapping_address_write */
           (mapping_address_write + nb_write) > mb_mapping->nb_registers) {
```
- `mapping_address < 0` appears twice; the second one was clearly meant to be `mapping_address_write < 0`.
- Only the upper bound of the write range is checked.
- So a crafted request with a valid read range and a write address below `start_registers` passes validation.
- The write loop then stores attacker-controlled register values at `tab_registers[negative]`. This is an out-of-bounds heap write (underflow), not just a read.
