The 300-byte write lands just past the 256-byte static buffer `addrstr`, at the `memcpy` on line 538 of `coap_resolve_address_info`. The host length comes from the attacker's Proxy-Uri and is never checked against the buffer size.

**How the report maps to the code**
- ASan reports a WRITE of size 300 starting exactly at the end of `coap_resolve_address_info.addrstr`. That buffer is `static char addrstr[256]`, declared at line 498 of `coap_address.c`.
- Frame #0 is in the `coap-server` binary. That is ASan's statically linked `memcpy` interceptor. The caller (frame #1) is in libcoap.
- The only write into `addrstr` with a caller-controlled length is line 538: `memcpy(addrstr, address->s, address->length);`. There is no bound check.

**How a network message reaches it**
1. A request arrives with a Proxy-Uri option. `coap_pdu_parse_opt_base` accepts Proxy-Uri lengths up to 1034 bytes.
2. In `coap_proxy_get_session`, `coap_split_proxy_uri` is called. In `coap_split_uri_sub`, the host is everything up to the next `:`, `/` or `?`, with no length limit (line 202).
3. Back in `coap_proxy_get_session`, only `host.length == 0` is rejected (line 266).
4. `coap_proxy_get_ongoing_session` passes `&server_use->uri.host` to `coap_resolve_address_info` (line 420).
5. A 300-byte host is then copied into the 256-byte static buffer.

A Uri-Host option would be capped at 255 bytes, but a host taken from Proxy-Uri bypasses that cap. The AF_UNIX branch checks `address->length >= COAP_UNIX_PATH_MAX`, but the normal getaddrinfo branch has no equivalent check.
