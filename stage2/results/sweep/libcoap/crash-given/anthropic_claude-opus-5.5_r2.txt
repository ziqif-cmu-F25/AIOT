**Analysis**

1. **What overflowed.** ASan reports a WRITE of 300 bytes into `coap_resolve_address_info.addrstr`. That is the `static char addrstr[256]` declared at `coap_address.c:498`. The write starts at offset 0, and the bad address is exactly 0 bytes past the 256-byte object.

2. **Which call wrote it.** Frame #0 is in the `coap-server` binary, which is ASan's `memcpy` interceptor. Frame #1 is inside libcoap. The only writes into `addrstr` are:
   - line 536: `memset` of `sizeof(addrstr)` (safe);
   - line 540: `memcpy` of 9 bytes for `"localhost"` (safe);
   - line 538: `memcpy(addrstr, address->s, address->length)`, with no length check.

   The 300-byte write can only be line 538.

3. **How a 300-byte host gets there.** The path is the proxy code:
   - `coap_proxy_forward_request_lkd` calls `coap_proxy_get_ongoing_session`.
   - That calls `coap_resolve_address_info(&server_use->uri.host, ...)`.
   - `uri.host` is filled by `coap_split_proxy_uri()` from the Proxy-Uri option.
   - Proxy-Uri may be up to 1034 bytes (`coap_pdu.c:1256`).
   - `coap_split_uri_sub` sets `uri->host` to whatever span precedes `:`, `/` or `?`, with no length limit (line 202).
   - `coap_proxy_get_session` only checks `host.length == 0` (line 266).

   So a Proxy-Uri like `coap://AAAA…(300 chars)…/` gives a 300-byte host. (Uri-Host via Proxy-Scheme is capped at 255 by option validation, so it cannot trigger this.)

4. **Secondary bug.** Even a host of exactly 256 bytes would leave `addrstr` without a NUL terminator before `getaddrinfo`. The check therefore needs to be `>=`, not `>`.
