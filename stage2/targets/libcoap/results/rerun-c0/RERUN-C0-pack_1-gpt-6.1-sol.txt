1. file: src/coap_address.c / function: coap_resolve_address_info / approx line: 620–630
   bug class: Global/static buffer overflow; possible unterminated-string out-of-bounds read.
   reasoning (quote the specific code line(s) involved):
   ```c
   static char addrstr[256];
   ...
   memset(addrstr, 0, sizeof(addrstr));
   if (address && address->length)
     memcpy(addrstr, address->s, address->length);
   ...
   error = getaddrinfo(addrstr, NULL, &hints, &res);
   ```
   There is no check that `address->length < sizeof(addrstr)`. More than 256 bytes overwrites adjacent static storage. Exactly 256 nonzero bytes removes all termination within `addrstr`, potentially making `getaddrinfo()` read beyond it.

   how untrusted input reaches it (trace the data flow):
   `coap_proxy_forward_request_lkd()` → `coap_proxy_get_ongoing_session()` → `coap_proxy_get_session()` → `coap_split_proxy_uri()` sets `server_use->uri.host` to an attacker-controlled substring → `coap_resolve_address_info(&server_use->uri.host, ...)`.

   The supplied PDU validation permits Proxy-Uri values up to 1034 bytes, and URI parsing imposes no 255-byte hostname limit. Thus this does not require an oversized Uri-Host option.

   triggering input characteristics:
   A request to a proxy configured in a `*_STRIP` mode, containing a syntactically accepted Proxy-Uri such as `coap://` followed by more than 256 hostname bytes. The hostname need not resolve: the overflow happens before DNS resolution. Applies to the non-RIOT, non-Contiki resolver implementation.

4. file: src/coap_uri.c / function: check_segment; consequentially decode_segment / approx line: 490–515
   bug class: Off-by-one out-of-bounds read; conditional size_t underflow and runaway memory access.
   reasoning (quote the specific code line(s) involved):
   ```c
   if (*s == '%') {
     if (length < 2 || !(isxdigit(s[1]) && isxdigit(s[2])))
       return -1;

     s += 2;
     length -= 2;
   }
   ...
   --length;
   ```
   Reading `s[2]` requires at least three remaining bytes, but the check only rejects lengths below two. With a two-byte tail such as `%A`, `s[2]` is outside the supplied segment.

   If that out-of-segment byte happens to be hexadecimal, validation continues: `length -= 2` produces zero, and `--length` wraps to `SIZE_MAX`. The loop then scans beyond the input. The decoder has corresponding unchecked subtraction:
   ```c
   while (length--) {
     if (*seg == '%') {
       *buf = (hexchar_to_dec(seg[1]) << 4) + hexchar_to_dec(seg[2]);
       seg += 2;
       length -= 2;
   ```

   how untrusted input reaches it (trace the data flow):
   Network-derived URI path/query supplied to `coap_split_path()` or `coap_split_query()` → `write_option()` → `make_decoded_option()` → `check_segment()` and, after successful validation, `decode_segment()`.

   triggering input characteristics:
   A path/query segment ending in `%` plus one hexadecimal digit, with its supplied length ending immediately after that digit. An adjacent hexadecimal byte can additionally activate the unsigned-underflow path.

   Reachability qualification: this requires an application to use the exposed split helpers on network-derived strings. The supplied built-in proxy forwarding path uses `coap_path_into_optlist()` / `coap_query_into_optlist()` instead, so it does not establish that call chain by itself.
